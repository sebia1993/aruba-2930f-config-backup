## 1. 배경 및 개발 목표

현재 프로젝트는 스위치 설정 백업, 포트·PoE 관리, LLDP 조회, 물리 링크 확인, 케이블 진단, 자동 모니터링 및 수동 작업 예약을 제공한다. 추가 기능의 목적은 운영자 PC가 아니라 **각 스위치가 직접 NMS 서버로 ICMP Echo Request를 전송**하여 스위치 관리망의 통신 상태를 확인하는 것이다.

주요 목표:

- NMS 서버 한 대를 기본 목적지로 지정하여 다수 스위치에서 통신을 일괄 점검한다.
- 필요할 때 여러 서버(NMS, Syslog, AAA, AirWave 등)를 동시에 등록하여 같은 절차로 점검한다.
- 스위치의 SSH 접속 IP를 Ping 출발지 IP로 자동 지정하는 것을 기본값으로 하며, 일반 Ping과 직접 Source 지정도 지원한다.
- 독립된 `Ping 테스트` 메뉴와 이해하기 쉬운 옵션 설명을 제공한다.
- ICMP 응답 없음, 패킷 손실, SSH 접속 실패, CLI 오류 및 결과 미확인을 서로 구분한다.
- 유한한 장시간 테스트로 조합별 최대 10,000회 Ping 시도를 누적하고, 개별 측정의 시각·RTT·결과를 영속 저장한다.
- 장애·복구 관측 시각, 연속 손실, 동일 시간대 다중 스위치/목적지 상관관계, NMS 알람 및 중간 관측 지점 비교로 장애 의심 구간을 제시한다. 원인을 확정하거나 장비 변경을 자동 실행하지 않는다.
- 실행 전에 목표 조합·전체 시도 수·예상 소요시간을 확인하고, 실행 후 전체/장비/목적지별 실제 진행률, 경과 시간, 예상 남은 시간 및 예상 종료 시각을 제공한다.
- 기존 모니터링 및 수동 제어 기능을 보존하고 실제 운영 장비의 설정을 변경하지 않는다.

**판정 한계:** ICMP 성공은 해당 출발지와 목적지 간 Echo 요청·응답이 관측됐음을 의미한다. SNMP Polling/Trap, Syslog, AAA 등 실제 서비스의 정상 여부 또는 NMS에서 시작하는 세션의 허용 여부까지 보장하지 않는다. ICMP 무응답만으로 서버 장애, 방화벽 차단, 라우팅 장애 중 특정 원인을 확정하지 않는다.

## 2. 범위 및 기준 상태

### 2.1 포함 범위

- 로컬 웹 독립 메뉴 및 직접 진입 가능한 화면 경로(예: `#ping`). 기존 메뉴와 동일한 테마·반응형 구조 사용.
- Aruba 2930F/2930F VSF 및 현재 로컬 웹에서 지원하는 2930M-24G-PoE+ (JL320A)와 검증된 스택 구성.
- IPv4 기반 단일/다중 스위치 × 단일/다중 목적지 수동 Ping 테스트.
- 기존 SSH 계정 세션, 호스트키 검증, 장비 식별, 접근 제어, 작업 조정 및 대상 프로필 재사용.
- 옵션별 클릭형 도움말, 전체 옵션 설명, 기본·고급 옵션 분리, 프리셋, 명령 미리보기/복사.
- 실시간 진행률, 결과 목록/서버별 매트릭스, 필터, 상세 결과, 재실행, Excel 출력 및 목적지 프로필.
- 유한한 장시간 Ping(1회 명령 반복, 조합당 최대 10,000회), 시계열 기록/분석, SQLite 보존, 장애·복구 타임라인, 동시 장애 히트맵.
- NMS 장애 이력 Excel/CSV 수동 가져오기, 동일 시간축 비교, 공통 상위 구간 분류 및 중간 관측 지점 Ping/Traceroute 수동·제한적 자동 진단(상세 §15~19).
- 장시간 테스트의 실행 전 예상시간 계산, 실시간 카운트다운/ETA 보정, 전체·장비·조합별 진행 상태 및 예상 종료 일시, 일시정지·재개(상세 §20).

### 2.2 제외 범위

- 종료 조건이 없는 24시간 상시 관제, 자동 재시작 및 문자/메일 등 외부 장애 알림. 단, 사용자가 시작한 유한한 장시간 Ping 세션의 주기 실행과 이력 분석은 포함한다.
- Windows 데스크톱 EXE UI에 동시 기능 추가(공통 코어 변경 시 기존 데스크톱 회귀 테스트는 포함).
- IPv6, DNS 이름 기반 테스트, 네트워크 대역 자동 스캔, SNMP/UDP/TCP 서비스 헬스체크, NMS API 직접 연동. Traceroute는 검증된 읽기 전용 명령으로만 범위에 포함한다. OOBM 전용 Source 옵션은 별도 호환성 확인 후 확장 대상으로 둔다.
- `data-fill`, IP source routing, ToS 등 고급 트래픽 조작 옵션 및 임의 CLI 입력.
- 장비 설정 모드 진입, `write memory`, ACL/VLAN/라우팅 변경.
- 실제 사내 장비 검증 및 실운영 장시간 부하 검증: 사용자 직접 수행. 개발자는 모의 장비·CI 결과를 실장비 검증으로 대체해 주장하지 않는다.

### 2.3 기존 저장소와의 관계

기준 main에는 #123 수동 접수 복구, #124 케이블 진단 진행 조회 제한, #125 백업 폴더 선택창 전면 표시 변경이 병합되어 있다. #124/#125는 기준 공개 웹 릴리즈보다 이후 변경이다. 개발 착수 시 최신 main, 열린 PR, CI 상태, 배포 요청 정책을 다시 확인한다. 기존 Paramiko 4.0.0 및 구형 SSH의 제한적 호환 정책을 유지하며, 별도 의존성 업그레이드 PR을 자동 병합하지 않는다.

## 4. 사용자 화면 및 사용 흐름

### 4.1 메뉴 배치

```text
포트·PoE 관리
케이블 진단
스위치 컨피그 백업
Ping 테스트                 ← 신규 독립 메뉴
(기존 나머지 메뉴는 유지)
```

독립 메뉴 내부의 탭/화면 구성(기존 사이드바에 6개 메뉴를 추가하지 않는다):

```text
Ping 테스트
 ├─ 일반 통신 테스트
 ├─ 장시간 Ping 테스트
 ├─ Ping 이력 분석
 ├─ 동시 장애 분석
 ├─ NMS 장애 이력 비교
 └─ 경로 진단
```

```text
┌─ Ping 테스트 ──────────────────────── [전체 옵션 설명] ┐
```

### 4.3 입력 및 실행

1. 대상 스위치 IP를 한 줄씩 입력하거나 기존 대상 목록을 불러온다. 기존 프로필의 포트 목록은 Ping 대상에서 제외하고 IP/SSH 포트 기준으로 중복 제거한다. 포트·PoE 관리의 기존 프로필을 덮어쓰지 않는다.
2. 목적지 IPv4를 한 줄씩 입력하거나 서버 이름과 IP를 등록한다. 기본 화면에서는 NMS 한 대를 쉽게 입력하고 `서버 추가`로 확장한다. 이름은 표시용 별칭이며 CLI에 포함하지 않는다.
3. 프리셋을 선택하거나 옵션을 수정한다. 명령 미리보기, 예상 테스트 조합 수, 장시간 모드의 조합별 목표·전체 시도 수·예상 소요시간을 자동 갱신한다(§20).
4. 입력 오류 및 중복을 확인하고, 유효한 대상과 Source 모드를 실행 전에 표시한다. 대상/옵션은 접수 시 불변 스냅샷으로 확정한다.
5. 일반 Ping은 **Ping 시작**에서 현재 입력을 검증하고 접수한다. 명령 미리보기는 선택 사항이다. SSH 계정이 없으면 그 자리에서 기존 계정 입력창을 열며, 적용하면 이어서 실행하고 취소하면 측정을 접수하지 않는다. 시작 버튼 옆에 진행 상태와 처리 건수를 표시한다.
6. 장비별 진행 상태와 결과가 확정되는 대로 표시한다. 일반 목록 입력에서는 스위치별 SSH 세션을 재사용하고, 장비표 입력에서는 §4.5에 따라 목적지 역할별 세션을 동시에 연다. 장시간 모드는 실제 실행 속도에 맞추어 전체·장비·조합별 ETA를 재산정하며, 사용자가 일시정지·재개할 수 있다.
7. 완료 후 결과를 검색/필터링하고 필요한 조합만 재실행하거나 Excel로 저장한다.

### 4.4 표시 방식

- 서버 한 대: 스위치별 목록을 기본 표시. 스위치 이름/IP, Source, 응답, 손실률, 평균 RTT, 상태를 우선 보여준다.
- 서버 두 대 이상: 스위치 행 × 서버 열 매트릭스와 상세 목록을 전환한다. 셀은 `5/5 · 0% · 1ms`와 상태명/아이콘을 표시하며 색상만으로 구분하지 않는다.
- 상세: 목적지 IP, Source 요청값/확인 여부, 명령, 송수신 수, RTT Min/Avg/Max, 시작·종료 시각, 오류 사유 및 제한된 CLI 결과.
- 모바일: 가로 스크롤이나 서버별 카드/목록을 사용하여 정보 잘림 방지. 결과 필터와 선택 상태는 화면 전환 시 유지한다.

### 4.5 장비별 엑셀 입력

- 일반·장시간 Ping에서 한 행을 한 스위치로 읽는다. 기본 입력 화면에 엑셀 머리글과 장비 행을 붙여넣으면 자동으로 읽는다. 열 순서가 바뀌어도 이름으로 찾고, 작업자가 열을 직접 지정하면 즉시 반영한다.
- 장비 Hostname은 표시 이름이다. SW IP는 SSH 접속 및 기본 Source에 사용하는 IPv4다. GW IP, BB, NMS server는 같은 행의 게이트웨이, 백본, NMS 서버 IPv4다. 빈 목적지는 건너뛰고 잘못된 주소와 중복 SW IP는 원본 행과 열에 표시한다.
- 작업자는 장비 행과 GW·BB·NMS 역할을 선택한다. SW IP에 선택한 역할 수만큼 독립된 SSH 세션을 동시에 연다. 각 세션은 해당 역할의 목적지만 측정한다. 주소가 같아도 역할별 결과와 재실행 범위를 분리한다. 장시간 Ping은 각 측정 회차에 새 세션을 열며, 동시 SSH 한도 안에서 같은 행을 함께 시작한다. 미리보기와 장시간 총 시도 횟수는 이 규칙을 적용해 계산한다.
- 일반 Ping의 실패·선택 재실행은 원래 실행에서 해당한 장비와 목적지 조합을 사용한다. Excel 출력은 새 파일에 장비별 입력 순서와 역할별 결과를 유지하고, 상세 시트에 측정 근거를 남긴다.

## 5. CLI 옵션 및 기본값

### 5.1 기본 옵션

| 옵션 | 의미 | 장비 문서상 범위 / 기본값 | 프로그램 초기 권장값 |
|---|---|---|---|
| 목적지 | ICMP 요청을 받는 서버 IP | IP 또는 Hostname / 필수 | IPv4 필수, 단일·다중 |
| `repetitions` | Echo Request 반복 횟수 | 1~10,000 / 1 | 일반 5회; UI 1~100회. 장시간 모드는 CLI 1회씩, 총 목표 1~10,000회/조합 |
| `timeout` | 각 요청의 Echo Reply 대기 제한(전송 간격 아님) | 1~60초 / 5초 | 2초; UI 1~10초 |
| `source` | ICMP 출발지 IP 또는 VLAN에 할당된 IP | 장비 소유 IP/VLAN, 미지정 시 장비 선택 | SSH 접속 IP 자동 대입 |
| `data-size` | ICMP 데이터 영역의 크기(Byte) | 0~65,471 / 0 | 장비 기본값(옵션 생략); 고급 UI 0~1472 |
| `data-fill` | 데이터 패턴 지정 | 문서상 최대 1024 / 빈 문자열 | 미지원 |

장비 지원 범위와 프로그램 운영 상한을 구분한다. 상기 CLI 문법은 HPE 공식 AOS-S 16.11 가이드 및 2930F/M 16.10 가이드 기준이다. WC.16.01.0008 등 구형 OS 및 모델별 옵션 문법·출력은 실제 장비 또는 신뢰할 수 있는 버전별 자료로 확인해야 한다. 호환성을 확인할 수 없는 옵션은 사용 불가 또는 별도 오류로 표시하며 무단 대체하지 않는다.

### 5.2 Source 정책

| 모드 | 동작 |
|---|---|
| 스위치 접속 IP 자동 지정(기본) | 각 장비의 SSH 접속 대상 IPv4를 해당 장비의 `source` 값으로 대입 |
| 스위치 자동 선택 | `source` 옵션을 생략하고 장비의 기본 동작에 따름. 실제 Source가 출력되지 않으면 미확인 표시 |
| 직접 IP 지정 | 스위치별 Source IP 매핑 입력. 모든 장비에 한 IP를 무조건 적용하지 않음 |
| VLAN 지정 | VLAN ID를 입력하고 해당 장비의 VLAN IP로 Ping. 유효한 IP가 있는지 확인 |

`show ip` 등 모델/OS에서 검증된 읽기 전용 명령을 활용해 명시 Source IP가 스위치에 할당되어 있는지 확인한다. SSH 접속 IP가 NAT/VIP/가상 주소로 인해 장비 자체의 주소가 아닌 경우도 있으므로 단순 가정하지 않는다. Source 확인 실패, VLAN IP 없음 또는 미지원 옵션 발생 시 해당 조합을 별도 오류로 종료하고 일반 Ping으로 자동 전환하지 않는다. Source 지정은 기존 라우팅이나 방화벽을 우회하지 않으며, 실제 선택된 Source 또는 확인 불가 상태를 결과에 기록한다.

### 5.3 실행 명령 예시

```text
# NMS 서버 1대, SW-01 / SW-02에서 각각 실행
ping 198.51.100.10 repetitions 5 timeout 2 source 192.0.2.11
ping 198.51.100.10 repetitions 5 timeout 2 source 192.0.2.12

# 목적지 서버 추가: 같은 SW에서 각 명령을 순차 실행
ping 198.51.100.20 repetitions 5 timeout 2 source 192.0.2.11

# 장비 자동 Source
ping 198.51.100.10 repetitions 5 timeout 2

# VLAN 지정(지원 확인 필요)
ping 198.51.100.10 repetitions 5 timeout 2 source 10

# 고급 Data Size 지정
ping 198.51.100.10 repetitions 5 timeout 2 source 192.0.2.11 data-size 1472
```

실제 실행에는 주석이 아닌 검증된 단일 Ping 명령만 전달한다. 1472 Byte는 IPv4 헤더 20 Byte + ICMP 헤더 8 Byte를 더하면 일반 MTU 1500에 해당한다. 단편화 방지(DF)가 확인되지 않는 경우 큰 Ping 성공을 경로 MTU 정상으로 단정하지 않는다.

### 5.4 프리셋

| 프리셋 | 반복 횟수 | Timeout | Source | Data Size |
|---|---:|---:|---|---|
| 빠른 통신 점검 | 3 | 1초 | 접속 IP 자동 | 장비 기본값 |
| 일반 통신 점검(기본) | 5 | 2초 | 접속 IP 자동 | 장비 기본값 |
| 상세 통신 점검 | 20 | 3초 | 접속 IP 자동 | 장비 기본값 |
| 사용자 지정 | 직접 설정 | 직접 설정 | 선택 | 선택 |

프리셋 선택 시 모든 관련 옵션이 함께 반영된다. 값을 수동 변경하면 `사용자 지정`으로 전환한다. 기본 프리셋으로 돌아가는 기능을 제공한다. 고급 옵션 영역을 접어도 이미 적용된 옵션은 유지하며, 현재 설정 요약과 명령 미리보기에 표시한다.

## 6. 도움말 및 UX 상세 설계

각 옵션명 옆에 클릭 가능한 `ⓘ 도움말`을 배치하고 해당 항목 아래에 설명 영역을 펼친다. PC 마우스, 키보드 및 모바일 터치에서 동일하게 접근할 수 있도록 하며 Hover만으로 작동하는 툴팁은 보조 수단으로만 사용한다.

| 항목 | 클릭 시 설명 내용 |
|---|---|
| 반복 횟수 | 요청 전송 횟수, 5회 기본 권장, 간헐 손실 시 10~20회, 증가 시 소요 시간 증가 |
| 응답 대기 시간 | 각 응답 대기 제한, 사내망 2초 제안, 전송 간격과 구분, 설정과 실제 응답 지연의 차이 |
| Source | 자동 접속 IP 지정 / 장비 자동 선택 / 직접 IP / VLAN의 차이, 장비 소유 IP 조건, ACL 및 관리망 진단 활용 |
| Data Size | 데이터 영역 크기, 일반 점검 기본값, 1472 Byte 및 MTU의 관계, 단편화 관련 한계 |
| 목적지 | 단일/복수 IPv4 등록 방법, NMS 서비스 상태 자체를 검증하지 않는다는 주의 |

도움말 공통 구조: 의미 → 장비 지원 범위 → 장비 기본값과 프로그램 권장값 → 활용 사례 → CLI 예시 → 주의사항. 문구는 한국어로 정적 리소스에 포함하고 외부 인터넷 없이 읽을 수 있게 한다. 화면 상단 `전체 옵션 설명`으로 모든 항목을 한 번에 펼치거나 닫을 수 있도록 한다. 도움말 열기/닫기와 테마 변경은 입력값 및 실행 상태를 변경하지 않는다. 버튼의 접근 가능한 이름과 `aria-expanded` 상태를 적용한다.

명령 미리보기는 실제 서버 명령 생성 규칙과 일치해야 한다. 첫 스위치 예시를 기본으로 하되 특정 장비/서버 조합도 확인할 수 있게 하고, 다수 장비 명령을 무제한 DOM에 생성하지 않는다. 복사는 미리보기 명령만 클립보드에 복사하며 실행 기능은 아니다.

## 7. 작업 처리 및 동시성 정책

### 7.1 권장 운영 상한(초기값, 변경 가능)

| 항목 | 제안값 |
|---|---|
| 최대 스위치 | 300대 |
| 최대 서버 | 10대 |
| 최대 조합 | 3,000건(300 × 10) |
| 동시 SSH 작업 | 기본 5세션 / 일반 Ping 최대 10세션, 기존 전역 SSH 한도 우선 |
| 동일 스위치 | 목록 입력은 목적지별 순차 실행. 장비표 입력은 선택된 역할별 독립 세션을 동시에 실행. 제어·진단·조회 작업과 기존 작업 조정기를 공유 |
| 명령 실행 제한 | 요청 수·Timeout 및 실제 CLI 동작에 따른 충분한 명령 deadline, SSH 연결 제한과 별도 |
| 취소 | 대기 중 미실행 취소, 진행 중에는 지원 확인된 중단 동작 또는 안전한 명령 종료 후 중단 |

일반 프리셋에서 스위치 300대와 서버 1대는 300개 조합, 3대는 900개 조합이다. 총 Ping 요청량은 조합 수 × 반복 횟수로 표시한다. 모든 요청이 Timeout일 때 단일 조합의 단순 대기 합계는 `repetitions × timeout`이지만, SSH 접속, 장비 응답, 스케줄링, 실제 CLI 처리 시간이 별도로 있으므로 전체 실행 시간을 보장하지 않는다. 대량 실행 시 예상 부하와 대상 수를 확인할 수 있게 한다.

### 7.2 실행 구조

```text
로컬 웹 브라우저
  → 입력 검증 및 작업 접수(API)
  → 기존 작업 조정기 / 전역·장비별 동시성 제한
  → SSH 연결 / 장비 모델·호스트키·Source 확인
  → 스위치별 Ping 실행(목록은 순차, 장비표는 GW·BB·NMS 역할별 동시 실행)
  → CLI 출력 파싱 / 결과 분류
  → 진행 이벤트 및 결과 저장·화면 갱신
  → 선택 재실행 / Excel 출력
```

- 기존 PoE OFF/ON 및 케이블 진단 예약의 FIFO, 중복 방지, 만료 정책을 훼손하지 않는다. 기존 수동 제어 요청을 Ping 대량 작업 때문에 장시간 지연시키지 않는다.
- Ping을 낮은 우선순위의 수동 읽기 전용 진단 작업으로 처리하고, 명령 사이/장비 작업 경계에서 기존 작업을 양보할 수 있도록 설계한다. 새로운 큐가 필요하다면 기존 큐와 동일한 전역/장비별 자원 잠금을 공유한다. Ping 대량 작업을 기존 24건 제어 예약 큐에 개별 조합으로 무단 적재하지 않는다.
- 기존 1분 자동 조회는 중복 회차가 누적되지 않도록 유지하며, 건너뛴 회차와 재개 여부를 기존 UI에서 확인할 수 있게 한다. 새로운 Ping 메뉴에서 현재 대기 사유도 표시한다.
- 접수 ID 기반 중복 방지, 브라우저 새로고침 및 접수 응답 유실 시 읽기 전용 상태 확인을 재사용한다. 동일 ID로 테스트를 중복 시작하지 않는다. 서버 재시작/계정 만료 시 미실행 작업을 자동 재개하지 않는다.
- 한 스위치 연결 실패는 다른 스위치에 전파하지 않는다. 전역 인증 거부 시 계정 잠금 방지를 위해 신규 SSH 연결을 일시 중단하고 사용자 조치를 요청한다.
- 진행 중 취소 또는 세션 유실로 완료 여부를 알 수 없으면 `결과 미확인`으로 기록한다. Ctrl+C 중단은 장비 호환성과 프롬프트 복귀가 확인된 경우만 사용하며, 장비 자체 재부팅이나 설정 변경으로 중단하지 않는다.

## 8. 결과 판정 및 데이터 모델

| 표시 상태 | 판정 기준 |
|---|---|
| 정상 | 완료된 유효 결과에서 모든 전송에 응답 수신 |
| 일부 손실 | 유효 결과에서 응답 1건 이상, 일부 요청 미응답 |
| 무응답 | 완료된 유효 결과에서 전송은 확인됐으나 Echo Reply 0건 |
| 목적지 도달 불가 | 장비가 명시적인 unreachable 오류를 보고. 송수신 통계가 없으면 손실률 미확인 |
| SSH 접속 실패 | 연결, 인증, 지문 또는 세션 확립 실패. 목적지 무응답과 분리 |
| Source 오류 | 지정 IP/VLAN이 유효하지 않거나 명령이 Source를 거부 |
| CLI 오류 / 미지원 | 권한·문법·버전 오류 |
| 결과 미확인 | 명령 deadline, 응답 유실, 통계 불완전, 파싱 불일치 등 |
| 대기/실행 중/취소/미실행 | 작업의 실행 상태를 통신 판정과 구분 |

손실률은 유효한 `sent > 0` 및 `received`가 확인된 경우에만 `(sent - received) / sent × 100`으로 계산한다. 응답이 없으면 RTT는 null(—)로 처리하며 0ms로 치환하지 않는다. 출력에 명시된 RTT 통계가 없지만 모든 성공 응답의 RTT가 완전하게 수집된 경우에만 Min/Avg/Max를 산출하고 출처를 표시한다. `<1ms` 표기는 원문 또는 별도의 상한 정보로 보존하고 임의로 0ms 처리하지 않는다. 단일 응답형 출력과 반복 출력 모두 지원하되, 불완전한 응답을 정상 또는 100% 손실로 간주하지 않는다.

권장 데이터 구조:

- `PingRun` (일반 모드; 장시간 세부 모델 §17): `run_id`, `request_id`, `status`, `created_at`, `started_at`, `finished_at`, `options`, `target_snapshot`, `total_pairs`, `completed_pairs`, `parent_run_id`(재실행 시).
- `PingResult`: `run_id`, `switch_ip`, `ssh_port`, `hostname`, `model`, `os_version`, `destination_ip`, `destination_label`, `source_mode`, `requested_source`, `source_verification`, `observed_source`(확인 가능한 경우), `sent`, `received`, `loss_pct`, `rtt_min_ms`, `rtt_avg_ms`, `rtt_max_ms`, `rtt_evidence`, `status`, `reason_code`, `reason_message`, `started_at`, `finished_at`, `duration_ms`.
- 조합 키: 스위치 IP + SSH 포트 + 목적지 IP(한 실행 내 중복 방지). 실행 ID를 분리하여 재실행 결과가 이전 결과를 조용히 덮어쓰지 않도록 한다.
- 실행 진행률은 종료된 조합 수 / 전체 유효 조합 수로 계산한다. 취소·미실행도 종료 상태로 정리하고 실제 수행 수를 별도로 표시한다.
- CLI 원문은 길이 제한 및 민감정보 제거 후 해당 세션의 상세 확인용으로만 노출한다. 로그 또는 외부 진단 파일에 자동 포함하지 않는다.

## 9. 프로필 및 결과 저장

- 기존 로컬 웹 데이터 디렉터리 `%LOCALAPPDATA%\Aruba2930FLocalWeb\data` 정책을 준수한다. 서버 프로필에는 이름/IPv4 및 옵션만 저장하고 SSH 비밀번호, 인증 토큰, 장비 원문 설정은 저장하지 않는다.
- 기존 대상 프로필과 호환되는 가져오기, 목적지 프로필 저장·불러오기, 입력 미리보기 및 중복 제거를 지원한다. 서로 다른 기능의 프로필을 무단 덮어쓰지 않는다.
- 실행 상태 및 최소 결과는 기존 작업 상태 저장 구조와 연계한다. 장시간 Ping의 개별 측정 및 장애 이벤트는 SQLite에 저장하며 기본 보존 기간 30일(제안), 일반 결과는 기존 정책에 맞추어 유지한다. DB 용량 상한·내보내기·명시적 삭제 및 보존 정책은 §17을 따른다. 종료 조건 없는 상시 관제는 범위 제외다.
- 일반 Excel `.xlsx`에는 `요약`, `상세 결과` 시트를 제공한다. 요약은 작업 ID, 시각, 옵션, 서버별 상태 집계; 상세는 스위치/목적지/Source, 응답·손실률·RTT, 상태, 오류 사유, 시각을 포함한다. 장시간 분석 Excel/CSV는 §17~19에 따라 원시 기록, 장애 이력, 비교 결과를 추가한다. 필터 전체 또는 선택 범위 내보내기를 구분하고 수치 필드는 숫자 형식으로 저장한다.
- Excel 수식 주입 방지(외부 입력 및 호스트명 등 문자열을 안전한 텍스트로 저장), CSV/JSON 등 외부 프로필 검증, 권한 있는 사용자의 다운로드만 허용한다.

## 10. 보안 및 운영 제약

- 기존 SSH 호스트키 검증, 변경 지문 차단, 장비 식별, 제한적 레거시 SSH 호환 및 계정 세션 정책을 유지한다. 비밀번호는 메모리에만 유지한다.
- 서버에서 IPv4, 정수 옵션, VLAN ID(장비 지원 범위), 장비 수, 서버 수 및 전체 조합 수를 재검증한다. 입력값에서 줄바꿈·제어문자·CLI 구분자 등 허용되지 않은 문자열을 제거하는 것이 아니라 거부한다. IPv4 유니캐스트 목적지로 제한하고 브로드캐스트/멀티캐스트 테스트는 금지한다.
- 명령은 검증된 값과 고정 CLI 템플릿으로만 생성한다. 사용자 제공 임의 명령을 받지 않는다. 모델/OS 허용 범위를 확인한 뒤 실행한다.
- 기존 로컬/공유 웹 접근 정책과 세션 검증을 동일하게 적용한다. 신규 API가 기존 인증/접근 경계를 우회해서는 안 된다. 외부 공개, 방화벽 자동 개방, 외부 서버 전송 및 신규 공유 권한 부여는 하지 않는다.
- 공개 GitHub 기록, 테스트 fixture, 스크린샷, 릴리즈에는 가상 IP와 합성 장비명만 사용한다. 실제 사내 주소, 개인 계정, 설정 원문 및 비밀값은 포함하지 않는다.

## 15. 장시간 Ping 테스트 (v1.1 추가)

### 15.1 목적과 실행 방식 확정

일반 모드는 기존 단기 반복 명령을 사용하고, **장시간 모드는 SSH 연결을 가능한 범위에서 재사용하면서 `repetitions 1` 명령을 반복**한다. 앞선 v1.0의 단기 모드나 단일 10,000회 명령을 장시간 모드의 기본으로 사용하지 않는다. 10~20회 묶음 수집은 향후 부하 개선 대안이며, 개별 관측 시각 정밀도가 낮아지므로 자동으로 전환하지 않는다.

```text
ping 198.51.100.10 repetitions 1 timeout 2 source 192.0.2.11
```

각 스위치/목적지/Source 조합에 대해 1회씩 실행한다. 정상·실패를 구분하는 목적은 같지만 장시간 모드는 시작/응답 시각과 관측 공백을 추가 기록한다. CLI가 `repetitions 1`을 지원하지 않는 경우 문법 확인 후 명시적 호환 어댑터를 사용하며, 미지원 옵션을 숨기거나 Windows Ping으로 대체하지 않는다.

| 설정 | 초기 권장값 / 정책 |
|---|---|
| 총 목표 횟수 | 조합당 1~10,000회, 기본 10,000회(장시간 모드) |
| 명령 반복 단위 | 1회 고정 |
| 목표 측정 주기 | 1 / 3 / 5 / 10초 선택, 초기 5초 권장(미확정) |
| Timeout | 2초 기본, 일반 모드와 동일한 입력 검증 |
| Source | SSH 접속 IP 자동 지정 기본, §5.2 동일 |
| Data Size | 장비 기본값, 고급 옵션에서 변경 |
| 대상 | 스위치·목적지 단일/다중. 일반 모드의 대상 상한과 별개로 장시간 실행량 제한 적용 |
| 실행 시간 한도 | 목표 횟수 및 별도 최대 실행 시간으로 유한하게 종료. 기본 48시간 제안, 사용자 설정 및 검증 후 확정 |
| 저장 | UTC 시각·millisecond 정밀도·SQLite 증분 저장 |
| 일시정지·재개 | 신규 명령 중지, 진행 중 명령은 안전 종료, 재개 시 목표·기록 유지 및 현재 기준 ETA 재산정(§20) |
| 중지 | 신규 실행 중지, 진행 중 명령은 안전 종료/결과 미확인 처리 후 부분 결과 보존 |

10,000회 × 1/3/5/10초의 단일 조합 이상적 소요시간(계획용 근사)은 각각 약 2시간 47분 / 8시간 20분 / 13시간 53분 / 27시간 47분이다. 실제 간격은 SSH 지연, Timeout, 대상 수, 장비 처리 시간 및 기존 작업 우선순위에 따라 길어질 수 있다. 전체 예상시간은 제한과 실제 작업 배치에 따라 달라지므로 §20의 계산 정책을 사용한다. 화면에 목표 간격과 실제 간격, 예정 대비 실행 지연, 실제 완료 예상 범위를 별도 표시한다. 이 값은 완료 보장이 아니다.

### 15.2 실행량 및 스케줄링

- 장시간 Ping의 단위는 장비 × 서버 × Source 조합이다. 사용자 확인 화면에서 조합별 횟수와 전체 명령 시도 상한(예: 3대 × 2서버 × 10,000회 = 60,000회)을 분리 표시한다. 관측 지점 Ping과 Traceroute는 별도 제한·건수로 집계한다.
- 목표 10,000회는 **조합별 명령 시도 상한**이다. 명령을 전송한 시점에 시도 번호를 할당하고, 실제 ICMP 전송/응답 확인 수, 미확인 시도, SSH 실패, 예정되었으나 미실행한 회차를 구분한다. 결과가 유실됐다고 동일 시도를 자동 재전송하거나 확인된 패킷 수를 채우기 위해 무제한 실행하지 않는다. 목표 도달, 최대 시간, 사용자의 중지 또는 안전 중단 시 종료한다.
- 같은 스위치의 여러 목적지는 순차 처리하고 장비 간에는 제한적 병렬 처리한다. `monotonic` 기반 스케줄을 사용하며 이전 명령이 끝나지 않았다면 새 명령을 중복 시작하지 않는다. 지나간 스케줄 슬롯은 미측정으로 기록하고 몰아서 실행하지 않는다. 놓친 슬롯이 길게 이어지면 구간/횟수로 압축 저장할 수 있다.
- 기존 작업 조정기의 전역/장비별 잠금, SSH 계정·호스트키 확인, 수동 제어 우선 정책을 공유한다. 장시간 세션이 장비 잠금을 계속 점유하지 않도록 명령 경계에서 양보하며, 기존 세션 재사용이 안전하지 않으면 종료/재연결한다. 목록 입력에서는 같은 장비의 명령을 순차 실행한다. 장비표 입력에서는 같은 행에서 선택한 GW·BB·NMS가 독립 SSH 세션으로 함께 시작한다. 장시간 Ping 작업은 낮은 우선순위로 처리한다.
- 초기 장시간 운영 제안: 동시 활성 SSH 최대 5세션(기존 전역 한도 우선), 전체 명령 시작 속도 초당 5건 이하. 같은 목적지 IP를 측정하는 서로 다른 행은 마지막 실제 전송 후 최소 0.5초 간격을 두며, 같은 행의 역할들은 목적지 IP가 같아도 함께 측정한다. 이는 실장비 검증 전 보수적 제안이며, 다수 대상에서 실제 간격이 늘어날 수 있음을 시작 전에 경고한다. 공통 시간대 비교가 목적이면 소수의 대표 스위치와 동일 시간창을 우선 확보한다. 전체 스위치 수백 대에 1초 간격을 보장하지 않는다.
- 정상 수동 PoE/케이블 작업이 들어오면 해당 장비의 Ping을 명령 경계에서 양보하고 자동 조회 정책을 보존한다. SSH 연결 실패·인증 거부는 제한적 지연 재연결 및 기존 인증 차단 정책을 따른다. 사용자가 장시간 작업 중지/취소하면 결과 보존 후 종료한다.
- v1.0의 브라우저 마지막 탭 종료 정책을 임의로 변경하지 않는다. 장시간 작업 중 마지막 탭 종료 시 신규 측정을 중단하고 현재 명령을 안전하게 정리한 뒤 저장된 부분 결과로 종료하는 정책을 제안한다. UI에 탭을 닫으면 장시간 측정이 종료될 수 있음을 안내한다. 서버 재시작 후 자동 재개하지 않고 기존 이력을 열 수 있게 한다. 장시간 측정의 무인 상시 실행은 별도 승인 범위다.

### 15.3 UI 및 진행 상태

```text
장시간 Ping 테스트
 ├─ 스위치 / 목적지 / Source 선택
 ├─ 총 목표 10000회 ⓘ | 목표 주기 5초 ⓘ | Timeout 2초 ⓘ
```

장시간 옵션 도움말에는 목표 주기와 Timeout의 차이, 횟수 단위, 실제 시간과 측정 누락, 수집 시각의 오차를 반드시 포함한다. 상태는 일반 Ping과 동일하게 색상만으로 전달하지 않는다.

## 16. 개별 Ping 시각 기록 및 장애 시간 판정

### 16.1 Timestamp의 정확도와 데이터 출처

HPE 문서의 기본 Ping 출력은 대상 주소, RTT 및 반복 시 순번 등을 보여주나 개별 패킷의 절대 전송 시각은 일반적으로 제공하지 않는다. 프로그램이 SSH 명령을 전송하기 직전과 결과를 수신할 때 수집 PC 시각을 기록한다. **이 값은 패킷 자체의 정확한 송수신 Timestamp가 아니라 명령 관측 범위**다. SSH 버퍼링·프롬프트 처리·장비 CPU 지연을 포함하므로 수신 시각에서 RTT를 빼서 실제 전송 시각을 추정값으로 확정하지 않는다.

1. 예정 시각(`scheduled_at_utc`)과 작업 대기 시작을 기록한다.
2. SSH 명령 전송 직전 UTC 시각(`command_started_at_utc`) 및 monotonic 기준점을 기록한다.
3. 실제 CLI 결과를 수신한 UTC 시각(`result_received_at_utc`), 명령 완료/프롬프트 복귀 시각(`command_finished_at_utc`) 및 monotonic 경과 시간을 기록한다.
4. 장비가 확인한 Ping RTT·명시적 응답 상태를 파싱한다. 성공 응답의 RTT는 SSH 명령 소요 시간으로 대체하지 않는다. 실제 패킷 송수신 시각은 신뢰할 수 있는 원천 증거가 없는 한 null로 저장한다.
5. 시작/결과 시각, 시각 출처, 관측 범위 및 파싱 근거를 한 건의 측정 레코드로 저장한다. 화면에 수집/감지 시각임을 표시한다.

시각 저장은 UTC(ISO 8601 또는 epoch milliseconds), 기본 표시 KST(Asia/Seoul, UTC+09:00)로 통일한다. 원본 NMS 시각 문자열/시간대는 보존한다. elapsed와 스케줄링은 monotonic clock을 사용하여 Windows 시계 조정으로 음수 간격이 생기지 않도록 한다. 벽시계와 monotonic 간 차이를 추적해 NTP 보정·시계 점프를 감지하면 해당 구간에 `CLOCK_UNCERTAIN` 표시를 붙이고 교차 장비/NMS 상관 분석 신뢰도를 낮춘다. 수집 PC·NMS·스위치 로그(사용하는 경우) NTP 동기 상태를 확인하는 체크리스트를 제공한다. 밀리초 저장 자릿수가 실제 밀리초 단위 정확도를 보장하지 않는다.

### 16.2 예시 (가상 기록, KST)

| 시도 | 명령 시작 | 결과 수신 | 상태 | 장비 RTT |
|---:|---|---|---|---:|
| 1 | 14:30:01.000 | 14:30:01.080 | SUCCESS | 1 ms |
| 2 | 14:30:06.000 | 14:30:06.095 | SUCCESS | 2 ms |
| 3 | 14:30:11.000 | 14:30:13.110 | TIMEOUT | — |
| 4 | 14:30:16.000 | 14:30:18.110 | TIMEOUT | — |
| 5 | — | — | NOT_MEASURED (PoE 예약) | — |
| 6 | 14:30:26.000 | 14:30:26.090 | SUCCESS | 1 ms |

예시 결과는 명령 결과 수신 시각 기준 최초 실패 14:30:13.110, 마지막 실패 14:30:18.110, 마지막 정상 14:30:06.095, 이후 최초 정상 14:30:26.090이다. 14:30:21 부근은 미측정이므로 전체 구간의 연속적인 물리 장애를 확정할 수 없다. 위 표의 미측정 행은 예정 슬롯의 표시이며 실제 시도 횟수로 세지 않는다. UI에서 예정 슬롯 번호와 명령 시도 번호는 별도로 관리한다.

### 16.3 상태·분모·장애 이벤트 규칙

| 상태 | 의미 | 손실률 처리 |
|---|---|---|
| SUCCESS | 해당 요청의 Echo Reply가 확인됨 | 성공 1건 |
| TIMEOUT | 장비가 해당 송신 요청의 무응답을 명시적으로 확인 | 미응답 1건 |
| UNREACHABLE | 목적지 도달 불가 보고 | 전송 증거가 확실한 경우만 별도 미응답 집계; 그 외 손실률 미확인 |
| SSH_ERROR / SOURCE_ERROR / CLI_ERROR | 접속·Source·권한/문법 등 오류 | 제외 |
| UNKNOWN | 명령이 전송됐으나 응답 또는 실제 전송 여부 미확인 | 제외, 별도 표시 |
| NOT_MEASURED | 작업 대기, 제한, 취소 등으로 명령 미실행 | 제외 |

유효 측정 분모는 송신과 성공 또는 무응답의 판정이 확인된 요청 수다. 확인된 손실률 = 확인된 미응답 / 유효 측정 × 100. 전체 시도/예정 대비 관측 커버리지, 오류 및 미측정 수를 함께 표시한다. 유효 관측이 없으면 손실률 `—`(판정 불가), 정상/0%로 표시하지 않는다. Unreachable은 명확한 별도 상태로 유지하고 실제 송신/응답 통계를 확인하지 못한 경우 분모를 만들지 않는다.

- 이벤트 원시 기준은 유효한 첫 무응답 관측으로 시작한다. 연속 실패 N회 이상을 `장애 의심`으로 강조(기본 3회 제안)하되 단발 실패를 숨기지 않는다. 성공 관측이 나오면 복구 관측으로 종료(기본 성공 1회, 필요 시 연속 성공 기준 변경 가능).
- 저장 필드: 마지막 정상 관측, 최초 실패 명령 시작/결과 수신, 마지막 실패, 최초 복구 명령 시작/결과 수신, 유효 연속 실패 횟수, 관측 지속 시간(최초 실패 감지부터 최초 복구 감지까지), 미측정 여부, 시각 불확실성, 이벤트 상태.
- 실제 장애 시작/끝은 관측 간격 및 SSH 지연 때문에 정확히 확정할 수 없다. 마지막 정상과 첫 실패 관측 사이, 마지막 실패와 첫 복구 관측 사이의 범위를 **추정 경계**로 보여준다. 관측 지속 시간은 실제 물리 장애 지속 시간과 구분한다.
- 미측정/UNKNOWN/SSH 오류는 연속 실패에 추가하지 않는다. 공백을 사이에 둔 실패를 연속 실패로 단정하지 않고 이벤트를 `관측 단절/불확실`로 구분한다. 이후 첫 정상은 `다시 정상 관측`이지 공백 중 실제 복구 순간이 아니다.
- 첫 측정부터 실패하면 시작 시점 미확인, 마지막 측정까지 실패하면 복구 미확인/진행 중으로 남긴다. 테스트 종료 후 복구되었다고 가정하지 않는다.
- RTT는 성공 관측값만 사용한다. Min/Avg/Max, P95/P99(정의와 유효 샘플 수 표시, 예: nearest-rank), 연속 변화 및 시간 버킷별 손실률을 계산한다. `<1ms`는 범위 정보로 보존하고 이를 임의 숫자로 치환하여 정확한 통계를 주장하지 않는다. 손실을 RTT 0 또는 매우 큰 임의값으로 표시하지 않는다.

## 17. 이력 저장·조회 및 분석 화면

### 17.1 SQLite 데이터 모델 및 보존

기존 DB 정책과 마이그레이션 구조를 먼저 검토하고, 다음 논리 엔터티를 신규 테이블 또는 동일 역할의 구조로 구현한다. UTC/monotonic 측정은 서로 다른 용도로 사용한다. monotonic 절대값은 서로 다른 프로세스/재시작 간 비교하지 않고 측정 경과 시간으로 저장한다.

| 엔터티 | 핵심 필드 |
|---|---|
| `ping_runs` | run ID, 종류, 옵션·대상 스냅샷, 상태, 시간 한도, 생성/시작/종료, 부모 실행 ID, 초기 ETA·가정/모델 버전, 누적 일시정지·경과시간 |
| `ping_series` | series ID, run ID, 스위치 IP/SSH 포트/hostname, 목적지 IP/별칭, Source 모드/값/검증, 목표 횟수·주기, 경로 그룹, 첫/마지막 시도 및 완료 시각, 상태·대기 사유 |
| `ping_run_state_events`(논리 엔터티) | run/series ID, 상태 변경 UTC, 사유, 일시정지/재개/대기/중지, 필요 시 ETA 스냅샷과 품질/갱신 시각; 매초 영속 기록하지 않음 |
| `ping_samples` | series ID, slot 번호, attempt 번호(nullable), 예정 시각, 명령 시작/결과 수신/종료 UTC, monotonic duration, observed RTT/근거, status/reason, 전송 확인, 시각 품질, 기록 시각 |
| `ping_observation_gaps` | series ID, 시작/종료 UTC, 건너뛴 슬롯 수, 이유, 시간 품질 |
| `ping_events` | series ID, 첫/마지막 실패, 마지막 정상, 첫 복구, 관측 시간 범위, 연속 실패 수, 상태·불확실성 |
| `nms_events` | 원본 파일/행 ID, 스위치 식별 키, 알람 유형, 발생/복구 시각 UTC, 원본 시각·시간대, 미복구 여부, 중복 키 |
| `path_profiles` / `path_runs` | 장비/그룹·관측 지점, 역할·Source, 기준/장애 시 진단 시각, hop 결과·명령/상태, 분석 근거 |

`series_id + slot`과 실행한 시도 번호의 유일성을 보장한다. 측정 전 명령 시도 상태를 기록하고 결과를 증분 반영해 갑작스러운 서버 종료 시 남은 진행 상태를 `UNKNOWN`으로 정리한다. 신규 실행은 별도 run ID를 사용한다. SQLite 트랜잭션, 제약조건, 단일 쓰기 큐 또는 기존 DB 동기화 구조, 인덱스(series/time, 상태/time, 장비/목적지) 및 스키마 마이그레이션을 검증한다. 진행 중 저장 실패·디스크 부족 발생 시 새 명령 실행을 중지하고 화면에 명시한다. DB 무결성을 확보할 수 없는 상태에서 측정을 계속하지 않는다.

- 장시간 이력 보존 기본 30일(제안). 기간 및 용량 상한 설정, 오래된 완료 실행의 정리, 사용자가 선택한 이력 삭제/내보내기를 지원한다. 보존 정리 중 실행 중 데이터는 삭제하지 않는다. 대량 측정 시작 전 예상 데이터 건수를 표시하고 실제 DB 크기 및 빈 디스크를 확인한다. 저장 용량 숫자는 실측 후 결정한다.
- 300 스위치 × 서버 10대 × 10,000회는 최대 3천만 시도이므로 일반 모드 대상 한도를 장시간 실행에 그대로 적용할 수 있다고 가정하지 않는다. 장시간 총 시도 상한과 DB 용량은 모의 부하 검증 후 확정하고, 초과 요청은 명시적인 제한 메시지로 거부한다.
- 조회는 페이지/시간 버킷 집계로 처리한다. 전체 데이터의 브라우저 로딩/DOM 생성을 금지한다. 그래프 집계 시 손실과 급증한 RTT가 평균화에 가려지지 않도록 구간별 최대 RTT·손실률·관측 건수 및 미측정 표시를 포함한다.
- 내보내기: `요약`, `개별 Ping`, `장애·복구 이벤트`, `동시 장애/관측 지점`, `NMS 비교`, `경로 진단` 시트 또는 CSV. Excel 행 한도(시트당 1,048,576행, 헤더 포함)에 맞춰 분할/CSV 대체를 제공한다. 대량 CSV는 스트리밍 생성하며 수식 주입 방지, UTC/KST 및 단위 표시, 빈값 보존 정책을 적용한다.

### 17.2 이력 분석 UI

- 상단 요약: 목표 시도/실제 시도, 성공, 확인된 손실, 오류/미확인, 미측정, 유효 손실률 및 커버리지, 현재/최대 연속 실패, 최근 장애·복구 관측.
- RTT 그래프: X축은 관측 시각(KST), Y축은 장비가 보고한 ms. 실패는 별도 마커/손실 구간, 미측정은 회색 공백으로 표현한다. 시간 범위(최근 15분/1시간/전체/사용자 지정)와 스위치·목적지·Source 필터를 제공한다.
- 장애 타임라인: 마지막 정상, 첫 실패, 마지막 실패, 첫 복구 관측 및 불확실 구간을 강조한다. 이벤트 선택 시 관련 원시 Ping 기록으로 이동한다.
- 동시 장애 히트맵: 장비(또는 목적지) 행 × 시간 버킷 열. 정상/일부 손실/무응답/미측정/불확실을 글자·아이콘과 색상으로 구분한다. 버킷별 유효 관측 개수, 손실률, 관측 커버리지와 관련 NMS 알람을 클릭해 확인한다.
- 장시간 이력은 브라우저 재접속 및 서버 재시작 이후 조회할 수 있다. 진행 중 화면 갱신 오류가 장비 명령 재실행을 일으키지 않도록 기존 요청 ID 및 상태 조회를 사용한다.

## 18. 동시 장애 및 NMS 장애 이력 상관 분석

### 18.1 비교 단위와 데이터 준비

같은 시간대에 여러 스위치가 같은 NMS 대상으로 무응답을 기록하면 공통 경로 이상 가능성을 높이는 증거가 된다. 그러나 Ping 단독 결과만으로 특정 물리 링크/장비 장애를 확정할 수 없다. 스위치→NMS Ping과 NMS→스위치 모니터링 방향은 서로 다르며, 비대칭 라우팅, ICMP 정책, NMS Polling 방식·스케줄·알람 임계치 및 CPU 부하가 영향을 줄 수 있다.

- 사용자가 스위치별 사업장·건물·상위 백본/업링크 그룹 및 관측 지점 역할을 등록한다(선택, 없으면 미분류). 스위치 호스트명만으로 상위 경로를 자동 확정하지 않는다. 실시간 LLDP/토폴로지는 검증된 증거가 있는 경우만 보조 정보로 사용한다.
- 기본 시간 버킷 1분 제안, 5초/10초/30초/1분/5분 등 선택. 실제 샘플 주기보다 과도하게 좁은 버킷에는 미측정이 많아지므로 관측 수와 품질 표시. 명령의 시작/결과 수신 관측 구간을 보존하고 여러 버킷을 걸치면 불확실성을 표시한다.
- 동시 이벤트 판단은 실제 관측 시간창의 겹침, 유효 측정 커버리지, 시계 상태 및 그룹 정보를 사용한다. 시간 차 허용값은 측정 주기/SSH 지연/ NMS Polling 주기와 알람 지연을 고려하고 사용자 조정 가능(초기 ±60초 제안, 확정 아님). 허용값을 넓혔다는 이유만으로 원인 일치로 판정하지 않는다.
- 공통 장애 후보는 같은 목적지와 공통 시간창에 확인된 실패가 있는 2대 이상부터 표시(최소 장비 수 제안). 영향 장비/유효 관측 장비/미측정 장비 수, 정상 그룹, 동시성 시간창, 근거와 반증을 함께 출력한다. 순차 측정으로 실제 관측 시간창이 겹치지 않으면 `동시성 확인 불가`로 표시한다.

### 18.2 NMS 이력 파일 가져오기

CSV로 장애 발생·복구 이력을 수동 등록한다. 실제 NMS 파일 샘플은 아직 없으므로 필수 컬럼 매핑 UI를 제공하고 특정 NMS 포맷을 가정하지 않는다.

| 입력 필드 | 용도 |
|---|---|
| 장비 IP 또는 검증된 고유 ID | 스위치 이력과 연결, hostname 중복 확인 |
| 이벤트 종류/메시지 | 예: Ping Fault Occurred / 복구; 종류와 원본 메시지 보존 |
| 발생 시각 | UTC 정규화 후 비교 |
| 복구 시각 | 비어 있으면 미복구/미확인 |
| 시간대 | 원본에 없으면 운영자 확인, 임의 UTC/KST 해석 금지 |
| Polling 주기/임계치(선택) | NMS 알람의 감지 지연 해석 |

가져오기 전 헤더/시간대/장비 매칭 미리보기, 날짜 파싱 오류, 복구가 발생보다 앞선 기록, 중복과 모호한 매칭을 표시하고 유효한 행만 승인 후 반영한다. 발생/복구가 분리된 알람은 장비 키·종류·시각을 이용하되 복수 후보가 있으면 운영자 확인을 요구한다. 원본 파일/행 ID 및 가져오기 시각을 보존하며 중복 재가져오기 방지. Excel 수식·매크로 실행 금지, 업로드 크기 제한 및 서버측 파서 안전성 검증.

### 18.3 분석 결과 분류 및 출력 예시

| 관측 패턴 | 우선 점검 후보 | 반증·추가 확인 |
|---|---|---|
| 단일 스위치에서 NMS 및 비교 목적지 실패 | 해당 스위치, 관리 VLAN, 업링크 또는 공통 초입 | 동일 그룹 정상 장비, 링크/오류 카운터 확인 |
| 동일 상위 백본 그룹 여러 대의 동시 손실 | 공통 백본/업링크/상위 경로 | 다른 그룹 정상 여부, 공통 토폴로지 확인 |
| 다른 백본 그룹에서 동시에 NMS만 실패 | NMS 접근 경로/서버/공통 정책 | 다른 서버 및 중간 지점 성공 여부, NMS 부하/정책 |
| NMS 알람과 스위치→NMS 손실 시간창 겹침 | 양방향 경로/서버/공통망 이상 가능성 | 알람 Polling 주기, 반환 경로, 실제 NMS 로그 |
| NMS 알람 동안 스위치→NMS는 정상 관측 | NMS Polling/ICMP 방향별 정책·경로 차이 | NMS→스위치 요청 및 응답 확인, 수집 커버리지 확인 |
| 동시성 부족·시계 오류·SSH 실패만 존재 | 판정 보류 | 유효 관측 확보 및 시간 동기화 |

자동 분석 리포트는 `의심 구간`, `관측 근거`, `정상/반증`, `관측 공백`, `시간 오차`, `다음 확인 항목`을 포함한다. 신뢰도는 정량적인 근거(관측 커버리지, 비교 지점 수, 시간창 겹침, 토폴로지 확인)로 낮음/보통/높음 또는 판정 보류로 표시하되 정확한 원인 확률로 표시하지 않는다. 임의의 백분율로 원인을 확정하지 않는다.

## 19. 경로 진단 및 단계적 장애 구간 좁히기

### 19.1 비교용 관측 지점 구성

기본 목적지는 NMS 서버 1대다. 필요할 때 운영자가 백본/기본 게이트웨이/방화벽의 관리 또는 라우팅 인터페이스 IP, 동일 경로상의 비교 서버를 관측 지점으로 등록한다. 비교용 IP가 실제 경로상의 장비인지 확인하고 ICMP 응답 허용 여부 및 정상 기준을 사전 측정한다. 동일 Source와 동일/가까운 시간창을 사용하며 별도 표준 토폴로지를 가정하지 않는다.

```text
SW 관리 IP ── 업링크 ── 백본/게이트웨이 ── 방화벽/라우터 ── NMS
     │                       ↑                   ↑             ↑
     └── 동일 Source 기반 관측 지점 Ping ─────────┴─────────────┘
```

| 백본/게이트웨이 | 방화벽/중간 L3 | NMS | 분석 후보(확정 아님) |
|---|---|---|---|
| 정상 | 정상 | 무응답 | 최종 경로·NMS 서버 또는 NMS ICMP 정책 |
| 정상 | 무응답 | 무응답 | 중간 L3 이후 공통 경로, 방화벽 정책 |
| 무응답 | 무응답 | 무응답 | 초입 공통 경로 또는 스위치 관리망/업링크 |
| 무응답 | 정상 | 정상 | 중간 장비 자체의 ICMP 응답 제한 가능성 |
| 미측정 | 정상 또는 미측정 | 무응답 | 증거 부족, 비교 지점 측정 필요 |

중간 장비의 관리 IP 응답과 transit forwarding은 별개이며, 각 IP의 라우팅/반환 경로가 다를 수 있다. 이 표는 경로와 정상 기준이 확인된 경우의 우선 확인 후보일 뿐이다. 실제 장애 판단에 장비 로그, 포트 에러/드롭 카운터, LAG/STP/OSPF 이벤트, NMS 서버 상태 등 추가 증거가 필요하다.

### 19.2 Traceroute 연계

HPE AOS-S 16.11 WC 문서의 Source 지정 문법을 참고한다. 실제 장비 OS 지원을 확인한 고정 템플릿만 사용한다. 예시:

```text
traceroute 198.51.100.10 source 192.0.2.11
```

- 정상 시 기준 경로를 수동 저장하고 장애 관측 시 같은 Source/목적지에 대해 제한적으로 재측정해 hop IP, 응답·지연, 진단 시각을 비교한다. CLI 원문 단위를 확인하여 RTT 단위를 정규화한다.
- 기본은 수동 진단 및 사용자 선택형 자동 추가 진단(기본 OFF 제안)이다. 자동 모드를 활성화한 경우 연속 실패 임계치 도달 후 같은 장비/목적지의 중복 진단을 억제한다. 초기 제안: 이벤트당 1회, 같은 조합 최소 5분 간격, 전역 동시 1개, 제한된 hop/probe/timeout 및 전체 deadline. 명령 문법/출력 및 실제 처리 시간 검증 후 확정한다.
- 같은 장비의 다른 Ping/PoE/케이블 명령과 충돌하지 않도록 기존 작업 조정기를 이용한다. Source IP를 자동으로 바꾸거나 `ip-option` 등을 통한 경로 강제 변경은 하지 않는다.
- Traceroute는 L3 hop만 관측하고 L2 스위칭 구간을 모두 드러내지 않는다. ICMP rate-limit, UDP/ICMP 차이, 방화벽, ECMP 및 비대칭 경로 때문에 중간 hop 무응답 또는 지연만으로 고장 장비를 확정하지 않는다. 뒤 hop이 정상 응답하는 경우 앞 hop의 응답 제한 가능성을 우선 표기한다.
- 장애 중 진단하지 못하고 복구 후 실행된 경우 `복구 후 관측`으로 구분한다. 기준 경로 없음, 미지원 명령, 중단 및 응답 미확인을 별도 표시한다. Ping 손실 발생 시점과 진단 실행 시각의 차이를 저장한다.

### 19.3 완료 기준 및 결정 사항

승인된 방향(v1.1 유지): Ping 전용 메뉴에 일반/장시간 테스트, 1회씩 최대 10,000회 누적, 시간 기록, 이력·동시 장애·NMS 비교 및 경로 진단을 통합한다. 구현 시 기존 일반 기능과 장시간 모드를 구분하고, 장애 의심 구간을 근거와 함께 제시한다. v1.2에서는 §20의 ETA/진행률 요구사항을 추가한다.

아직 현장 검증 또는 세부 확정이 필요한 항목: 실제 WC 구형 OS/2930M CLI 출력, SSH 버퍼링과 전송 간격, NMS 원본 파일 형식과 Polling 정책, 스위치별 실제 토폴로지/비교 지점, 목표 주기·실행 시간 제한·동시성 및 전송량·DB 보존량·장애 임계치·상관 허용값. 위 제안값은 개발 착수 후 안전성 및 실측으로 조정한다. 자동 CI에서 가상 10,000회 시나리오와 회귀를 검증하되, 실제 운영망에서의 장시간 검증은 사용자 수행 범위다.


## 20. 예상 측정시간·실시간 ETA 및 진행 관리 (v1.2 추가)

### 20.1 확정된 기능 방향

사용자가 승인한 방향은 **공통 설정 + 조합별 독립 측정 + 장비별 집계 + 전체 작업 진행률 및 ETA**다. 반복 횟수와 주기를 모든 대상에 공통 적용하되, 각 장비·목적지·Source 조합이 별도의 목표와 카운터를 가진다. 단일 NMS 목적지에서는 장비별 목표 횟수와 조합별 목표 횟수가 같다. 여러 목적지에서는 장비 한 대의 목표가 해당 장비에 할당된 조합별 목표의 합이다. 한 장비의 미측정, 지연, 장애로 다른 장비의 횟수를 변경하지 않는다.

- 시작 전: 설정을 변경하는 즉시 조합 수, 조합별 목표, 총 명령 시도 상한, 장비별/전체 예상 소요시간과 예상 종료 일시를 갱신한다.
- 시작 후: 최초 예상시간과 현재 예상 남은 시간(ETA), 실제 경과 시간, 예상 종료 일시, 전체 진행률, 장비별 진행률·ETA, 목적지별 상세, 실제 측정 간격·대기 사유를 함께 보여준다.
- 화면은 초 단위 카운트다운을 제공하되, 서버 측 측정 및 스케줄러 상태를 바탕으로 ETA를 주기적으로 보정한다. 실제 완료 시각의 보장이 아니다.
- 사용자는 일시정지·재개·중지를 사용할 수 있다. 일시정지와 강제 중지/서버 종료는 구분한다. 기존 안전 정책과 실행 한도를 변경하지 않는다.

### 20.2 실행 전 예상시간 계산

아래 동일 장비 순차 실행 예시는 목록 입력 기준이다. 장비표에서는 한 행의 역할들이 동시에 실행되며, 같은 IP를 사용하는 역할은 행·회차당 한 번만 목적지 간격 계산에 포함한다. 전체 전송량은 역할별로 센다.

입력: 유효 스위치 수, 장비별 목적지/Source 조합 수, 조합별 목표 시도 N, 목표 시작 간격 I(초), Timeout, 동일 장비 순차 실행, 전역 동시 명령/SSH 한도, 전체 및 목적지별 명령 시작 속도 상한, 예상 CLI 처리 및 접속 준비 시간, 최대 실행 시간. 입력 정규화·중복 제거 후 유효 대상 기준으로 계산한다.

| 표시 항목 | 계산 및 의미 |
|---|---|
| 조합 수 | 실제 유효한 스위치 × 목적지 × Source 조합 수(대상별 예외 반영) |
| 전체 목표 시도 수 | 모든 조합의 목표 N 합계. 단일 명령당 1회인 장시간 모드 기준; 실제 전송 확인 수와 구분 |
| 조합별 이상적 시간 | 계획용 근사 N × I; 즉시 첫 실행이면 정확한 이상적 시작 간격의 합은 (N−1) × I이고 마지막 명령 처리 시간을 더함 |
| 장비별 예상시간 | 동일 장비 순차 명령, 대상별 주기, 다른 작업 대기 및 제한을 반영한 최종 조합 완료 예정까지 |
| 전체 예상시간 | 공유 자원/동시성/전송량 제한하에서 마지막 대상까지 종료될 예정 시간(makespan) |
| 예상 종료 일시 | 현재 또는 실제 시작 시각 + 예상 남은 시간; KST 날짜 및 시각 표시, UTC 원본 보존 |
| 부하 및 제약 | 예상 명령 시작량, 한도 초과 여부, 목표 주기 유지 가능성, 실행 시간 한도 및 저장 용량 경고 |

단일 장비의 N × I 값은 이해를 돕는 이상적인 참고치이며, 모든 대상에 대한 보장 시간이 아니다. 단일 목적지에서 I=5초, N=10,000회라면 약 13시간 53분 20초다. 실제 명령은 시작 시각 기준의 목표 주기를 따르고 Timeout은 별도 제한이다. N × (I+Timeout)으로 항상 계산하지 않는다. 명령 종료 후에 다시 I를 기다리는 고정 지연 방식도 기본으로 하지 않는다.

**계산 모델:** 실제 스케줄러의 작업 단위(명령 경계에서 조합을 번갈아 실행), 동일 장비 잠금, 전역 슬롯 및 목적지별 제한을 그대로 반영하는 추정기를 구성한다. 초기에는 확인 가능한 장비/CLI 프로파일 및 보수적인 처리 시간 가정으로 예상 범위를 계산하고 가정/품질을 표시한다. 검증된 관측치가 있으면 활용한다. 간단한 검산으로 전체 소요시간이 최소한 단일 조합의 측정 주기, 장비별 누적 명령 점유 시간, 전체/목적지별 전송량 제한에 따른 소요시간 등을 충족하는지 확인한다(첫 요청 burst/준비시간·최종 명령 완료 경계 고려). 이러한 하한을 더하거나 곱해 확정적인 ETA로 표시하지 않는다.

고정 그룹을 순차 실행하는 경우에만 `N×I×ceil(스위치 수/동시 장비 수)×서버 수`를 단순 예시로 사용할 수 있다. 이번 기본 실행 구조는 조합 간 명령 단위 교차 스케줄링이므로 위 수식을 그대로 실제 ETA 산출에 사용하지 않는다. 장비별 여러 목적지를 번갈아 실행해도 각 조합의 목표 주기 유지가 가능한지는 동일 장비 CLI 점유 시간과 제한에 의해 결정된다.

| 가상 입력 | 총 목표 시도 | 시간 해석 |
|---|---:|---|
| 1대 × 1서버, 10,000회, 5초 | 10,000 | 이상적 약 13:53:20 |
| 5대 × 1서버, 10,000회, 5초, 동시에 실행 가능 | 50,000 | 이상적 약 13:53:20; 5배로 늘어나지 않음. 목적지에 평균 1회/초 수준, 설정된 속도 상한 이내라는 가정 |
| 20대 × 1서버, 10,000회, 5초 | 200,000 | 5초 주기 유지에 평균 4회/초 필요. 목적지별 초기 제한 2회/초라면 전체 처리에 최소 약 27시간 47분(준비/최종 처리 등 제외)이 필요한 수준; 13:53:20 보장 불가 |
| 5대 × 2서버, 10,000회, 5초 | 100,000 | 장비별 20,000회, 조합별 10,000회. 장비 내 순차 처리 및 공유 슬롯·목적지 제한에 따라 전체 ETA 달라짐 |

위 표의 수치는 예시이며 실장비 성능 검증 결과가 아니다. 목표 횟수와 최대 실행 시간(기존 48시간 제안)이 충돌할 가능성이 있으면 시작 전 경고하고, 예상 완료 보장 없이 부분 종료될 수 있음을 표시한다. 장시간 실행 상한/전송량 정책을 ETA를 맞추기 위해 자동 완화하지 않는다. 비정상적으로 많은 조합은 검증된 운영 상한대로 거부하며, ETA 계산 자체가 수천만 시도 단위의 동기 시뮬레이션으로 UI를 차단하지 않게 한다.

### 20.3 진행률·측정 결과 카운터

| 구분 | 정의 |
|---|---|
| 목표 | 접수 시 확정한 조합별 명령 시도 상한 N; 실행 도중 임의로 줄이지 않음 |
| 시작된 시도 | 명령이 전송되어 시도 번호가 할당된 건. 결과 대기 중 포함 |
| 처리 완료 시도 | 시작된 시도가 성공/무응답/도달 불가/결과 미확인 등 종료 상태에 도달한 건 |
| 진행률 | 처리 완료 시도 ÷ 목표 × 100; 조합별·장비별·전체 동일 원칙 |
| 유효 측정 | 실제 전송 및 응답/미응답 판정이 확인된 건(§16.3) |
| 미측정 | 명령 미전송 슬롯·사전 SSH 오류·작업 대기. 시도 목표를 자동 소진시키지 않음 |
| 현재 진행 중 | 시작된 시도 − 처리 완료 시도 |
| 남은 미실행 목표 | 목표 − 시작된 시도; ETA는 진행 중 명령의 남은 처리까지 추가 고려 |

진행률은 단순 성공률이 아니다. 결과 미확인 시도는 처리 완료로 기록할 수 있으나 유효 측정 및 손실률 분모에 포함하지 않는다. SSH 접속 실패 등 명령 이전 오류는 별도 집계하고 제한적 재연결·시간 한도 정책을 따르며, 처리 완료 시도로 위장하지 않는다. 전체 진행률은 모든 목표의 합을 분모로 사용하고 완료 장비의 진행률 평균으로 계산하지 않는다. 장비 내 목적지가 여러 개면 해당 장비 조합들의 합으로 집계한다.

목표에 도달하고 모든 실행 명령이 종료되어야 목표 진행률 100%다. 100%라도 일부 결과가 미확인이면 상태 요약과 실제 유효 측정률을 별도로 표시한다. 사용자의 중지, 인증 중단, 최대 실행 시간 도달로 조기 종료된 경우 남은 목표를 자동 완료로 변경하지 않는다. 예: `부분 종료 · 4,000/10,000회 처리 · 40% · 미실행 목표 6,000회`. 이때 ETA는 `— (종료)`이며, 목표 정상 완료 시에만 `00:00:00 (완료)`로 표시한다. 단기 일반 Ping의 조합 단위 진행률(§8)은 별도 유지한다.

### 20.4 실시간 ETA 및 카운트다운 정책

1. 시작 시 초기 계산 가정 및 최초 ETA를 불변 값으로 남긴다. 별도로 서버의 최신 ETA/예상 종료 일시를 제공한다. 시계열 이력은 ETA 수정 근거까지 재현 가능한 수준으로 저장하되 매초 DB에 쓰지 않는다.
2. 실행 중에는 최근의 실제 명령 시작 간격, CLI 실행 시간(SSH 처리 포함), Timeout/실패, SSH 재연결, 대기·양보, 제한 속도, 남은 목표 및 다른 조합의 큐를 반영하여 재추정한다. 최근 유효 관측의 이동 통계/완료 처리율 등을 사용하되 일시정지·장기 차단 구간은 별도로 취급한다. RTT는 CLI 처리 시간이나 전체 시도 간격을 대신하지 않는다.
3. ETA 추정기는 가능한 한 스케줄러의 현재/예정 상태를 사용한다. 개별 조합의 남은 목표와 현실적인 처리율, 공유 병목 및 진행 중 명령의 잔여 처리 시간으로 장비별/전체 종료 예정 시각을 구한다. 완료된 장비는 잔여 부하에서 제거한다. 전체 ETA는 추정된 장비별 종료 일시 중 가장 늦은 것까지의 시간이며, 대기 장비와 공유 자원 경합을 누락하지 않는다.
4. 갱신 주기 제안: 결과 확정, 상태 변경, 스케줄 제약 변경 즉시 서버 스냅샷 갱신; 연속 실행 중에는 일정 간격(예: 5~15초)으로 재추정. 웹 화면은 최신 서버 값과 monotonic 경과 시간을 사용해 약 1초 단위로 카운트다운한다. 데이터 수집/통신 이벤트를 매초 생성하거나 장비 조회를 추가하지 않는다.
5. 새 ETA는 감소만 하는 값이 아니다. Timeout, 경쟁 작업, 실제 주기 증가 등으로 늘어날 수 있으며 `초기 예상보다 지연`, `재계산됨`, 대기 사유를 표시한다. 감소와 증가를 허용한다. 과도한 흔들림을 완화할 때도 실제 상태 변경/장기 지연을 숨기지 않는다.
6. 관측이 부족하면 `예상(초기 가정)` 또는 `계산 중`, 장기 대기/인증 오류 등 종료시각을 예측할 수 없으면 `산정 불가`로 표시한다. 신뢰도가 낮으면 단일 숫자보다 범위/근거를 표시한다. 근거 없는 완료 예정 일시를 제공하지 않는다.
7. ETA가 0에 도달해도 서버가 완료를 확인하기 전에는 완료로 표시하지 않는다. `재계산 중`으로 전환한다. UI가 오래된 서버 데이터를 받고 있거나 연결이 끊기면 `갱신 지연/연결 끊김` 표시와 마지막 갱신 시각을 유지하고 카운트다운을 정지한다. 다시 연결하면 서버 상태로 동기화한다. 브라우저 새로고침, 백그라운드 탭 제한, NTP 시간 점프가 측정 횟수 및 진행 상태를 바꾸지 않도록 한다.

### 20.5 상태·일시정지/재개 및 경합

| 상태 | 동작 및 표시 |
|---|---|
| 대기 중 | 아직 시작하지 않은 조합. 큐/예상 시작 또는 대기 사유 표시 |
| 측정 중 | 실제 처리량에 따라 진행 및 ETA 보정 |
| 작업 양보/재연결 대기 | PoE·케이블·자동 조회·SSH 재연결 등의 이유 표시; 예측 가능하면 ETA에 포함, 아니면 산정 불가 |
| 일시정지 요청/정리 중 | 새 명령 금지, 이미 시작된 명령을 안전하게 종료한 후 정지 |
| 일시정지 | 표시 카운트다운 정지; 마지막 예상 잔여 작업량 참고값 보존, 확정 종료 일시 숨김 |
| 재개 | 같은 run/series 및 목표/기존 이력 유지, 현재 시점부터 새 스케줄 및 ETA 산정, 건너뛴 과거 슬롯 재전송 금지 |
| 정상 목표 완료 | 잔여 0, 실제 종료 일시/총 경과 시간 및 유효 측정 요약 |
| 부분 종료/중지/오류 | 목표 미달이면 실제 완료율 보존, 종료 사유 및 부분 결과 제공, ETA 없음 |

일시정지는 우선 전체 장시간 테스트 실행 단위로 제공한다. 장비별 일시정지는 필수 범위가 아니며 개별 장비 대기 상태는 표시한다. 일시정지 후 장비 잠금을 해제하고 계정 및 호스트키 정책을 준수하며, 재개 전 인증/장비 상태를 다시 확인한다. 사용자 일시정지 중 관측 공백은 누락 구간으로 기록하되 통신 실패로 처리하지 않는다. 경과 시간은 실제 시작 후 벽시계 경과를 포함하고 별도로 활성 측정·대기·사용자 일시정지 시간을 구분한다. 사용자 일시정지로 기존 절대 실행 시간 한도를 무제한 연장하지 않는다(기본 한도는 시작부터의 실제 경과, 필요 시 별도 승인으로 변경). 브라우저 마지막 탭 종료·서버 재시작 시 자동 재개하지 않는 기존 정책(§15.2)을 유지한다.

### 20.6 UI 구성 및 가상 표시 예시

```text
Ping 테스트 > 장시간 Ping 테스트
[스위치 5대] [목적지 1대] [조합당 10,000회] [목표 주기 5초]
[Timeout 2초] [동시 측정 상한 5대] [Source: 관리 IP]
  전체 목표 50,000회 / 조합 5개
  조합별 이상적 시간 13:53:20 / 전체 예상시간 약 13:53:20
  예상 종료 YYYY-MM-DD HH:mm:ss KST / 예상 부하 및 한도 안내
  [시작]

실행 중
  최초 예상시간 13:53:20 | 실제 경과 05:33:20
  전체 진행 40.0% (20,000 / 50,000회)
  예상 남은 시간 08:21:40 | 예상 종료 YYYY-MM-DD HH:mm:ss KST
  성공 19,972 / 확인된 무응답 28 / 미확인 0 / 미측정 별도
  [일시정지] [중지]   마지막 갱신 HH:mm:ss
  장비       처리/목표        진행      ETA       손실   상태
  SW-01     4,000/10,000      40.0%     08:20:00     0    측정 중
  SW-02     4,020/10,000      40.2%     08:18:20     3    측정 중
  SW-03     3,980/10,000      39.8%     08:21:40    25    측정 중
  SW-04     4,000/10,000      40.0%     08:20:00     0    측정 중
  SW-05     4,000/10,000      40.0%     08:20:00     0    측정 중
```

예시 전체 ETA 08:21:40은 다섯 장비가 동시에 진행되고 추가 공유 병목이 없는 조건에서 가장 늦은 장비 기준이다. 실제 수치는 서버 스케줄러의 추정값을 사용한다. 장비 클릭/펼치기로 목적지별 목표·진행률·ETA·실제 시작 간격·대기 이유·상세 이력을 확인한다. 단일 NMS 모드에서는 중복되는 목적지별 열을 기본 숨김으로 유지하고, 다중 목적지에서만 펼칠 수 있게 한다. 대량 장비는 페이지/필터/집계로 표시하고, 완료/대기/지연 상태 검색을 지원한다. 최초 예상과 최신 예상을 혼동하지 않도록 라벨을 구분하고, 좁은 브라우저 화면에서도 남은 시간이 잘리지 않게 한다. 도움말에는 `ETA는 예측이며 늘어날 수도 있음`, `목표 주기와 실제 주기`, `조합당 횟수`를 설명한다.

### 20.7 개발·검증 및 승인 경계

- 서버 응답에 현재 목표, 시작/완료 시도·유효/미측정 카운터, 실행 상태/대기 사유, 초기 예상시간, 최신 ETA 초/예상 종료 UTC, 추정 시각, 품질/가정, 실제 측정 간격, 경과/일시정지 시간, 완료 일시를 포함하도록 기존 진행 API 구조를 확장한다. 장비별·조합별 스냅샷도 제공한다. API 명칭과 필드명은 현재 저장소 분석 후 결정한다.
- UI 상태 복원은 run ID 기반으로 서버에서 조회하고 클라이언트의 계산값으로 실행 상태를 수정하지 않는다. 일시정지/재개 요청은 기존 인증·요청 중복 방지·권한을 적용하고 중지 상태를 임의 재개하지 않는다.
- 초기 예상 모델과 실제 ETA 추정기의 자원 한도를 동일하게 적용하며, 가상 시계로 T24~T29 및 기존 T01~T23을 검증한다. 테스트에는 지연 후 ETA 증가, 대기 후 감소, 진행률 100% 이전 허위 완료 방지, 일시정지/재개, 다중 목적지, 제한에 따른 목표 주기 미달 및 실제 경과/예상 시간 차이를 포함한다. 실장비 성능 수치는 사용자가 검증한다.
- 수치 결정: 기본 5초/10,000회, 동시 SSH/전송량/실행 시간 한도 등 v1.1 제안값을 그대로 유지한다. ETA 재계산 주기(5~15초), 표시 품질 기준, 예측 처리 시간, 추정 방식의 세부 구현은 권장 설계이며 자동·현장 검증 결과에 따라 확정한다. 실제 진행 시 예측값은 보장하지 않는다.
- 이번 개정은 사용자가 승인한 ETA·진행 관리 기능만 확정 반영한다. 앞서 검토한 사업장 간 토폴로지 확장 및 추가 프리셋은 별도 승인 범위로 두며 기존 Ping/경로 진단 기능을 변경하거나 삭제하지 않는다.

**최종 목표:** 운영자가 `Ping 테스트` 독립 메뉴에서 스위치 관리 IP를 Source로 NMS 통신을 점검하고, 필요한 경우 조합별 최대 10,000회까지 개별 시각과 결과를 누적 기록한다. 장애·복구 관측 시간대, 연속 손실과 RTT 추세, 동일 시간대 여러 스위치의 결과, NMS 알람 및 중간 관측 지점의 증거를 한 화면에서 비교하여 장애 의심 구간을 좁힌다. 미측정 및 불확실한 상태는 명확히 분리하고 기존 운영 기능·보안·장비 안전성을 유지한다. 실행 전에는 현실적인 전체 예상시간을 제시하고 실행 중에는 전체·장비별 진행과 남은 시간을 실시간으로 표시·재산정한다. 이 계획서 작성은 실제 개발 착수 승인과 별개다.
