# 릴리즈 운영 원칙

## 목적

릴리즈는 개발 중 발생한 모든 작은 변경을 그대로 외부에 노출하는 기록이 아니라, **운영자가 실제로 내려받을 가치가 있는 검증 단위**로 관리합니다.

세부 개발 이력은 `CHANGELOG.md`와 Git 커밋에 남기고, GitHub Release는 운영 영향과 검증 결과를 중심으로 작성합니다.

## 버전 사용 원칙

현재 프로젝트는 `주버전.부버전.수정버전` 형식을 사용합니다.

예:

```text
0.2.0
0.2.1
1.0.0
```

### 수정버전

다음과 같은 실제 동작 오류 수정에 사용합니다.

- 특정 정상 장비 접속 실패 수정
- 설정 수집 누락 수정
- 결과 파일 저장 오류 수정
- 릴리즈 패키지 실행 오류 수정

문구 수정, 주석, 내부 정리만으로는 가급적 새 릴리즈를 만들지 않습니다.

### 부버전

운영자가 체감하는 기능이 묶여 추가될 때 사용합니다.

예:

- 새로운 장비 입력 방식
- 백업 결과 비교 기능
- 새로운 보고서 기능
- 운영 흐름에 영향을 주는 UX 개선

### 주버전

입출력 계약이나 운영 방식이 크게 바뀌는 경우에 사용합니다.

현재 0.x 단계에서는 호환성 변화가 생기면 Release Notes에서 명시적으로 안내합니다.

## 작은 변경 처리

다음 변경은 즉시 릴리즈하지 않고 `Unreleased`에 모으는 것을 기본으로 합니다.

- README/문서 수정
- 오탈자
- 표현 정리
- 개발자 편의 기능
- 사용자 동작에 영향이 없는 내부 리팩터링
- 테스트 보강만 있는 변경

여러 변경이 운영상 의미 있는 단위가 되었을 때 다음 릴리즈에 함께 포함합니다.

## 릴리즈 전 확인

릴리즈 자동화는 다음 검증을 통과해야 합니다.

- 태그가 annotated tag인지 확인
- 태그 커밋과 현재 `main`이 일치하는지 확인
- 버전 문자열 동기화
- 잠긴 의존성 설치
- 단위/통합 테스트
- 정적 검사
- 의존성 보안 감사
- Windows x64 패키지 빌드
- 실행 점검
- ZIP SHA-256 검증
- CycloneDX SBOM 생성
- `BUILD_INFO.json` 출처 검증

빌드 이후 `main`이나 태그가 바뀌면 게시를 중단합니다.

## GitHub 화면에서 발행

1. 버전·문서 변경을 모두 포함한 PR의 CI 통과를 확인하고 `main`에 병합합니다.
2. 병합된 `main` 커밋의 40자리 SHA를 확인합니다.
3. Actions → **Prepare release** → **Run workflow**에서 브랜치를 `main`으로 두고
   `release_tag`에 `v0.2.0` 같은 버전 태그, `expected_main_sha`에 확인한 SHA를 입력합니다.
4. 준비 작업은 버전 선언과 현재 `main`·선택한 실행·checkout·입력 SHA가 모두 같은지
   확인한 뒤 annotated tag를 생성하고, 해당 태그에서 기존 **Release**를 실행합니다.
5. **Release**의 Windows 빌드와 게시 작업이 모두 성공하고 세 배포 파일이 등록됐는지
   확인합니다. 준비 작업 성공만으로 배포 완료를 판단하지 않습니다.

준비 작업은 기존 태그를 덮어쓰거나 삭제하지 않습니다. 동일한 커밋의 annotated tag가
이미 있고 아직 Release가 없으면 준비 작업을 다시 실행하여 발행을 재요청할 수 있습니다.
태그가 다른 커밋을 가리키거나 lightweight tag이면 실패합니다. 빌드 중에는 `main`을
추가 변경하지 않습니다. 직접 annotated tag를 push하는 기존 발행 방식도 유지됩니다.

태그 생성·워크플로 실행 권한은 **Prepare release** 작업에만 부여합니다. 기존 Windows
빌드는 읽기 권한을 유지하고, 배포 파일 게시는 분리된 게시 작업에서만 수행합니다.
`GITHUB_TOKEN`으로 생성한 태그 push는 새 워크플로를 자동 시작하지 않으므로
[공식 이벤트 정책](https://docs.github.com/en/actions/concepts/security/github_token)에 따라
기존 Release를 태그 ref로 명시적으로 실행합니다.

## Release Notes 구성

GitHub Release 본문은 다음 순서를 기본으로 합니다.

1. 릴리즈 요약
2. 운영자가 알아야 할 핵심 변경
3. 운영 영향
4. 검증 결과
5. 다운로드 파일 설명
6. 설치/업데이트 방법
7. 알려진 제한
8. 상세 변경 이력 링크

개발 과정의 세부 방어 로직을 첫 화면에 모두 나열하지 않습니다.

## 보안 항목 사용 기준

CHANGELOG의 `보안` 항목은 실제 보안 경계가 바뀌는 경우에만 사용합니다.

예:

- 자격증명 노출 가능성
- SSH 장비 지문 검증
- 명령 허용 범위
- 의존성 취약점
- 민감 로그 노출
- 무결성/출처 검증

파일 이름이나 단순 UI 변경에서 기존 보안 경계가 유지되었다는 사실만으로 매번 `보안` 항목을 추가하지 않습니다.

## 사전릴리즈 상태

현재 자동화는 GitHub 사전릴리즈로 게시합니다.

이는 자동 검증이 부족하다는 뜻이 아니라, **실제 Aruba 2930F 운영 환경에 대한 현장 검증 범위가 아직 제한적이라는 사실을 구분하기 위한 상태**입니다.

현장 검증이 축적되면 다음 항목을 기준으로 정식 릴리즈 전환을 검토할 수 있습니다.

- 실제 2930F 단독 구성
- 실제 2930F VSF
- 여러 ArubaOS-Switch 버전
- 반복 장시간 수집
- 다수 장비 동시 수집
- 운영자 피드백
- 설치/업데이트 재현성

## 릴리즈 자산

일반 사용자가 받아야 하는 핵심 파일:

```text
Aruba2930FConfigBackup_vX.Y.Z_windows_x64.zip
```

검증용 부가 파일:

```text
Aruba2930FConfigBackup_vX.Y.Z_windows_x64.zip.sha256
Aruba2930FConfigBackup_vX.Y.Z_sbom.cdx.json
```

사용자는 ZIP과 `.sha256`을 우선 확인하면 됩니다. SBOM은 의존성 검토가 필요한 운영/보안 담당자를 위한 자산입니다.

## 기존 0.1.x 이력

초기 개발 단계에서 짧은 간격으로 생성된 0.1.x 릴리즈는 과거 기록으로 유지합니다.

기존 태그를 삭제하거나 변경하여 이력을 다시 쓰기보다, 이후부터 릴리즈 단위를 운영 관점에서 정리하는 방식을 사용합니다.
