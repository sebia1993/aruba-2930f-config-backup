# 의존성 감사 예외

이 문서는 자동 의존성 감사에서 일시적으로 제외하는 항목과 실제 실행 경로의
보완 통제를 공개합니다. 경고를 해결된 것으로 숨기기 위한 목록이 아닙니다.

## CVE-2026-44405

| 항목 | 내용 |
|---|---|
| GitHub Advisory | `GHSA-r374-rxx8-8654` |
| 대체 ID | `PYSEC-2026-2858` |
| 영향 의존성 | Paramiko 4.0.0 이하 |
| 현재 잠금 버전 | Paramiko 4.0.0 |
| 감사 심각도 | Low |
| 최초 검토일 | 2026-08-24 |
| 공개 자료 재확인 | 2026-09-08 |
| 다음 재검토 기한 | 2026-09-24 |

Paramiko 4.0.0은 RSA/SHA-1 서명 방식인 `ssh-rsa`를 허용합니다.
2026-09-08 재확인 결과, [PyPI에는 Paramiko 5.0.0이 공개되어 있으며](https://pypi.org/project/paramiko/5.0.0/),
[공식 변경 이력](https://www.paramiko.org/changelog.html#5.0.0)은 RSA/SHA-1 서명과
SHA-1 key exchange 지원 제거를 명시합니다. 따라서 수정 후보 배포가 없다는 이유로
예외를 유지할 수는 없습니다. 같은 날 [GitHub Advisory](https://github.com/advisories/GHSA-r374-rxx8-8654)의
`Patched versions`는 `None`으로 표시되어, upstream 배포 정보와 구분해 기록합니다.

현재 저장소는 4.0.0에 고정되어 있고 5.0.0으로의 잠금 파일 교체·SSH 회귀·Windows
패키지 검증이 완료되지 않았습니다. 아래 통제는 이 미해결 의존성의 임시 보완입니다.
5.0.0은 서명 외에도 KEX 지원을 변경하므로, 현재 연결·루프백 테스트와 레거시 장비의
호환성 경계를 검토하는 후속 업그레이드 작업이 필요합니다. 취약점 해결 완료나
5.0.0 호환성 검증 완료를 주장하지 않습니다.

## 보완 통제 (기본 엄격 SSH 경로 및 v0.9.2까지의 main)

- `disabled_algorithms`의 `keys`와 `pubkeys`에서 `ssh-rsa`를 비활성화합니다.
- 인증 전 호스트 키 사전점검과 실제 Netmiko 인증 연결이 같은 정책 함수를
  사용합니다.
- RSA/SHA-1 전용 서버는 사용자 이름이나 암호를 받기 전에
  `SSH_ALGORITHM_INCOMPATIBLE`로 종료합니다.
- SHA-256 호스트 키 지문을 별도 JSON 저장소에 고정하고, 변경된 키는 계속
  차단합니다.
- 보안 설정을 낮추는 자동 재시도나 대체 연결 경로를 제공하지 않습니다.
- 루프백 SSH 회귀 테스트와 생성된 연결 인자 테스트로 두 경로를 검증합니다.

`tools/validate.ps1`은 잠금 파일 감사에서 `CVE-2026-44405`만 제외합니다. 새 ID를
추가하거나 범위를 넓히려면 별도 보안 검토와 이 문서의 변경이 필요합니다.
GitHub Dependabot 경고는 수정 버전으로 교체할 때까지 열린 상태로 둡니다.

## 배포 경계

- 현재 `main`(v0.9.5): 기본 엄격 프로브를 우선 사용하며 서버 호스트키 불일치 시 인증 전 1회 자동 호환 연결을 시도합니다. 지문 신뢰 검증과 변경 키 차단은 유지합니다.
- v0.2.0 Windows 배포 소스: 위 보완 통제가 포함됩니다. 백업과 별도 포트 제어는
  같은 SSH 지문 저장소·RSA/SHA-1 차단 정책을 사용합니다. 실제 게시된 ZIP의
  `BUILD_INFO.json`, SHA-256 및 SBOM으로 해당 릴리즈의 출처와 의존성을 확인합니다.
- v0.1.8 Windows 바이너리: 위 보완 통제 이전에 생성되어 포함되지 않습니다.
- v0.2.0에서도 Paramiko 4.0.0 잠금과 `CVE-2026-44405` 감사 예외는 유지됩니다.
  포트 제어 추가나 새 배포만으로 의존성 취약점 해결을 주장하지 않습니다.
- 자동 테스트와 루프백 검증은 실제 Aruba 2930F 현장 검증을 대신하지 않습니다.

## 예외 제거 조건

다음 조건을 모두 충족하면 감사 예외를 제거합니다.

1. Paramiko 정식 릴리스의 upstream 수정 근거와 감사 결과를 대조함 (현재 검토 후보: 5.0.0)
2. `requirements*.txt`와 `pyproject.toml`을 같은 수정 계열로 갱신함
3. 호스트 키 사전점검, 인증 연결, 변경 키 차단과 Windows 패키지 검증을 통과함
4. `--ignore-vuln CVE-2026-44405`를 제거한 `pip-audit --strict`가 통과함
5. 보완 통제가 포함된 새 배포물을 만들고 SHA-256, SBOM, 출처를 검증함

5.0.0 후보가 확인되었으므로 후속 업그레이드 검증을 진행해야 합니다. 재검토일은
자동 연장하지 않으며, 완료 전에는 경고와 미검증 배포 경계를 계속 공개합니다.


## 2026-11-18 2차 재검토 메모

기존 문서의 재검토 예정일(2026-09-24)이 경과했습니다. B안 2차 안정화에서는 **Paramiko 4.0.0의 임시 예외·SSH 알고리즘 차단 통제를 변경하지 않고** Windows 전체 CI에서 기존 정책이 계속 작동하는지만 확인합니다. Paramiko 5.0.0은 별도 Dependabot PR #28에서 다루며, 이 안정화 PR에 고정 버전을 섞지 않습니다. 실제 Aruba 2930F OS 별 암호화 협상/접속 호환성 검증 없이는 해당 예외를 해제하거나 취약점이 해결됐다고 주장하지 않습니다.

후속 조치: Paramiko 5.x의 변경 이력·공식 보안 권고·사용 장비의 SSH KEX/host-key 호환성을 확인하고, 고정 의존성 전체·루프백 SSH/Windows EXE 검증 및 실제 현장 검증 뒤 감사 예외 제거 여부를 별도 승인받으십시오.


## v0.9.4 WC.16.01.0008 선택적 서버키 호환 예외 (2026-11-18)

HPE 공식 WC.16.08.0021 변경 이력은 RSA-SHA2 서버 호스트키와 추가 SHA-2 기반 KEX 지원 도입을 명시합니다. 실제 WC.16.01.0008 장비가 제공하는 알고리즘은 해당 스위치의 `show ip ssh`로 재확인해야 합니다. 문서 링크: https://arubanetworking.hpe.com/techdocs/AOS-Switch-RN/Content/16.08RN/WC/Enhancements.htm

- 기본 값은 호스트키와 사용자 공개키 인증 모두에서 `ssh-rsa`를 차단하는 기존 정책입니다.
- `레거시 SSH (장비별)`에서 IP:포트 정확한 확인 문자열을 직접 입력하여 명시 승인한 대상에 한하여 **서버 호스트키** `ssh-rsa`만 임시 허용합니다. 사용자의 `ssh-rsa` 공개키 인증은 여전히 금지합니다.
- 동의 범위는 현재 프로그램 프로세스의 IP:포트 allowlist입니다. 별도 파일, Windows 레지스트리, SSH 계정에 저장되지 않습니다.
- 예외 승인 전후 모든 연결의 호스트키 SHA-256 지문 최초 수동 승인/변경 차단, 명령 전 재검증, 일괄 PoE OFF LLDP 안전 가드가 동일하게 적용됩니다.
- `diffie-hellman-group1-sha1` 등 약한 신규 KEX를 활성화하지 않으며 자동으로 보안 수준을 낮추지 않습니다. 연결 실패가 KEX 또는 cipher 불일치 때문이라면 이 옵션만으로 해결되지 않습니다.
- 이 옵션은 취약점 보완책이 아니며 RSA/SHA-1 서명 위험을 재도입합니다. 장비 펌웨어 업그레이드가 장기 권장안입니다. 현장 실제 인증 및 PoE 제어 성공 여부는 운영자가 직접 검증합니다.


## v0.9.5 WC.16.01 자동 SSH 서버키 협상 (2026-11-18)

v0.9.4의 수동 승인 모드를 최신 사전 릴리스 v0.9.5에서 자동 연결 방식으로 변경했습니다.

- 매 SSH 서버키 사전 점검에서 먼저 `keys=[ssh-rsa]`, `pubkeys=[ssh-rsa]`를 차단한 엄격 연결을 시도합니다.
- 서버가 **호스트키 협상만** 거절한 경우(`no acceptable host key` / `no matching host key`)에는 인증정보 전송 전 최초 TCP 연결을 닫고 새 TCP 연결에서 **서버 호스트키** `ssh-rsa`만 허용하는 재협상을 최대 한 번 수행합니다.
- 성공한 대상 IP:SSH포트만 메모리에 표시합니다. 다른 장비는 엄격 모드를 유지하고 강한 협상에 성공하면 해당 장비의 이전 호환 표시를 해제합니다.
- 호스트키가 신뢰 등록되지 않았으면 기존 SHA-256 지문 승인 전 인증하지 않으며, 키 변경 시 즉시 차단합니다.
- KEX/cipher/TCP/Auth 오류에는 하향 재협상하지 않고, `diffie-hellman-group1-sha1` 등의 추가 약한 알고리즘을 지원하지 않습니다.
- 이 기능은 **RSA/SHA-1의 취약점을 해결하지 않습니다**. 오히려 일부 장비에 자동으로 SHA-1 서버 서명 사용 경로를 열어 주므로 강등 공격의 위험이 남습니다. 실제 운영 장비에서는 더 높은 버전의 AOS-Switch를 권장합니다.
- `pip-audit`에서 보류 중인 기존 `CVE-2026-44405` 예외를 삭제하거나 확장하지 않습니다. 사용자 공개키 인증의 `ssh-rsa`는 여전히 비활성화됩니다.

현장 WC.16.01.0008의 실제 지원 알고리즘과 네트워크 환경은 자동 루프백 검증과 별개로 실장비에서 확인해야 합니다.
